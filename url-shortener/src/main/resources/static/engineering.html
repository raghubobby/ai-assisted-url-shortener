Required scenarios

Three different engineering situations

Greenfield

New capability

Decompose a new URL-shortener capability, establish acceptance criteria, implement, and validate without unnecessary architecture.

  • Requirement normalization
  • API/schema design
  • Tests and release evidence
Brownfield

Existing-code change

Reason from the existing redirect/cache/data flow, find the smallest safe change, and prove no regression.

  • Impacted modules/data flows
  • Targeted fix
  • Regression and reliability checks
Ambiguous

AI surfaces unresolved product/security questions; the engineer makes the authoritative decision before implementation proceeds.

  • No invented requirements
  • Explicit assumptions

Selected decisions

Complexity was added only where justified

PostgreSQL is the source of truth.Durable URL mappings, idempotency, and analytics persistence.
Redis is optional.Redirect cache failures fall back to PostgreSQL instead of taking the service down.
No Kafka.No demonstrated throughput, replay, or multi-consumer requirement justified distributed messaging.
Database constraints own uniqueness.Short-code collisions are retried after the authoritative unique constraint detects them.
Versioned Flyway migrations are immutable.Schema corrections use forward migrations rather than rewriting applied history.
AI does not self-approve.Deterministic tests and engineer review provide the evidence used for acceptance.
Detailed evidence is retained in docs/ in the repository.
